# 日报质量闭环：分支贡献报告

> - 分支：`fix/daily-report-quality-closure`（基于 main@5132eb8，领先 48 个提交）
> - 日期：2026-08-09
> - 规模：288 个文件，+37,841 / −10,646 行；1 个奠基提交 + 46 个加固修复 + 1 个文档提交
> - 定位：给管理层的贡献说明——这个分支做了什么、为什么重要、验证到了什么程度、还卡在哪

## 0. 一页总结

**改造前**，日报生产线在报告写完之后还挂着一条复杂尾链（Scenario、Crux、Reflection、三个 Adaptor Reviewer、Forecast、Numeric Fidelity），多个模块各自产出结论和状态，导致报告正文、结构化评级、发布状态三者经常互相矛盾；报告正文里被追加机器 JSON；质量问题靠人工 Review 兜底，无法规模化。

**本分支把这条链改成了一个自动化的质量闭环**：完整报告草稿 → 六路并行审核 → 所有缺陷统一成 Issue → 按负责人打包修复（最多两轮）→ 独立复检 → 分级交付。两大核心机制：

1. **Issue 系统**——所有质量缺陷的唯一账本和唯一修复权威。六路审核发现的问题统一规范化、语义去重、按负责人路由修复；Issue 只能由独立复检关闭，修复者不能自证。
2. **Scoreboard 评分审计**——三个专职评分 Agent 按固定量表（Data 24 项 / Industry 24 项 / Company 28 项）逐项打分，作为质量审计依据展示；分数本身不控制流程，低分必须转成带证据和验收标准的具体 Issue 才能触发返工。

**验证程度**：928/928 后端测试、零警告 lint、16 份固定样本零网络重放、W8 证据门禁，全部绑定同一提交通过；随后用**真实的调度入口跑通一次完整 Daily One live 验证**——1 个 Idea → 1 个 Project → 1 份 21,102 字节的报告，经过两轮自动修复，0 个 Critical Issue，`decisionReady=true`，全程消耗 541 万 token（授权上限 1,000 万），约 70 分钟；最后用真实浏览器（桌面 + 移动）做了产品面验收并修掉两个 UI 缺陷。

**主要卡点**：分支尚未合并、生产环境还在跑旧链路；live 样本只有 1 份，Daily 100 稳定性未证明；单份报告 87 个 Major Issue 和三个 F 级评分说明「能交付」不等于「内容质量高」，评分严格度与 Issue 严重度映射需要校准；单报告 541 万 token 的成本直接放大到 Daily 100 不可行。详见第 10 节。

### 0.1 术语表

| 术语 | 含义 |
|---|---|
| Draft | Report Composer 生成的完整报告草稿。每轮生成都作为不可变版本存档（内容指纹 digest 固定），审核和发布用的是同一份字节。 |
| 六路审核 | 对同一份 Draft 并行运行的六个只读检查 Agent：三个 Reviewer + 三个 Scoreboard Evaluator。 |
| Reviewer | 跨领域问题审核者，共三个：Evidence（证据/数字/引用）、Requirement（需求/必需章节覆盖）、Logic（因果链/估值逻辑）。只发现和复检问题，无发布权。 |
| Scoreboard Evaluator | 内容质量评分者，共三个：Data / Industry / Company，各按固定量表逐项打分并输出具体缺陷。 |
| Scorecard / rubric | 评分量表（v3.1）。每项 rubric 有权重（合计强制等于 100）和 0–4 评分，程序按整数基点算总分、上限（cap）和质量等级（A–F band）。 |

| Issue Ledger | 所有 Issue 的统一账本（`issue-ledger.v1`），跨修复轮次保留完整生命周期。 |

| owner | Issue 的修复负责人：data / industry / company / report 之一。由服务端根据证据路径推导，模型无权指定。 |
| Owner Repair Packet | 修复包：同一负责人每轮的全部待修 Issue 合并成一份完整指令包，上游 Agent 一次处理。包内容是纯服务端投影，模型文本不能成为执行授权。 |
| verifier | Issue 的复检者。Issue 只有在指定复检者于新一版 Draft 上给出带证据的 resolved 结论后才能关闭；修复者自报完成无效。 |
| Unified Review Bundle | 一轮审核的封印产物：9 个不可变工件引用（3 Reviewer 结果 + 3 Scorecard + Issue Ledger + 修复任务表 + 修复包集合），身份与评审顺序无关。 |

| digest / ArtifactRef | 内容指纹与不可变工件引用。整条链的可信度基础：审核对象、发布对象、Conclusion 来源必须是同一 digest 的同一份字节。 |

## 1. 改造前的问题（main 上的旧链路）

main 上的 Run Analysis 是 9 节点拓扑、24 个活跃 Agent，报告写完后还要经过一串后置模块，问题集中在五点：

1. **多个权威、互相矛盾**。Scenario、Reflection、Forecast、Numeric Fidelity 各自生成结论或状态，报告正文说一套、结构化评级说一套、发布状态又是一套，没有一个统一事实。
2. **报告正文被机器数据污染**。旧的报告组装器直接把 Forecast JSON、Adaptor 反思、决策快照追加进 Markdown 正文——交付给用户的文件里混着内部机器对象。
3. **报告可用性被 Conclusion 绑架**。`reportReady` 依赖 Conclusion 成功：结构化结论一挂，一份本来完整可读的报告就整个消失。
4. **质量问题靠人工兜底**。Human Review / waive / bypass 语义贯穿执行器和状态机，报告质量最终取决于有没有人来看，无法支撑 Daily 100 的规模目标。
5. **Issue 分散且无生命周期**。审核发现的问题散落在 reviewer 输出和 checkpoint 里，没有统一身份、去重、路由和关闭标准；修复靠往共享 brief 里拼零碎指令。

此外，审核对象本身不稳定：`report/report.md` 是可覆盖的工作文件，审核看到的版本和最终发布的版本没有字节级绑定。

## 2. 新主链：一次分析怎么跑

新拓扑是 `run-analysis.v2@2.3.0`（10 节点），Agent 注册表从 24 个定义精简到 20 个（删除 7 个低收益尾链 Agent，新增 3 个 Scoreboard Evaluator），主链实际使用 13 个。一次完整运行：

1. **研究**：Data 先行，Industry 和 Company 基于同一份 Data 闭包并行分析。
2. **成稿**：Report Composer 读取三路研究产物，一次生成完整可读的 Draft，作为不可变版本提交（旧版本保留历史）。
3. **六路审核**（`evaluate-report` 节点）：三个 Reviewer + 三个 Scoreboard Evaluator 并行、只读地审核**同一个 Draft digest 及其依赖闭包**；同时运行确定性质量审计（第 4.3 节）。六路输出的候选缺陷全部进入下一步，任何单个 Agent 都没有发布权。
4. **确定性聚合**（`aggregate-review` 节点）：纯代码（无模型）把六路发现规范化、语义去重、合并进 Issue Ledger，生成修复任务表和每个负责人一份的 Repair Packet。
5. **封印**（`review-report` 节点）：校验后封成 Unified Review Bundle（9 个不可变引用），评审完成顺序不影响结果身份。
6. **收敛判定**：修复包为空 → 收敛，进入交付；否则进入修复波次，**最多两轮**。
7. **修复波次**：有 Data 包先只修 Data，新 Data 提交后 Industry/Company 基于同一新 Data 并行修复；Data 不变则命中的分支直接并行；上游完成后 Report Composer 重新生成整份 Draft，六路审核**先逐项复检旧 Issue、再全量扫描新问题**。
8. **交付**：把审核通过的 Draft **按字节原样**发布为带时间戳的报告文件；`qualityStatus` 由未解决 Issue 严重度计算。
9. **只读 Conclusion**：最后从最终报告提取结构化结论，绑定报告 digest；它不能改报告，失败也不影响报告可读。

整条链上，收敛与否只由「验证过的修复包是否为空」决定——执行器甚至会在模型或文本试图声明收敛时直接报错。这保证了终止条件是代码事实，不是语言表述。

## 3. 核心贡献一：Issue 系统——质量缺陷的唯一账本和唯一修复权威

代码主体：`backend/src/workflows/run-analysis/reviewers/`（issueLedger.js 743 行、issueIdentity.js 564 行、ownerRepairPacket.js 569 行等）+ 7 个新 JSON Schema 合同。

### 3.1 三个来源，一个账本

Issue 来自三处：三个 Reviewer（跨领域问题）、三个 Scoreboard Evaluator（低分维度的具体缺陷）、以及六条**确定性门禁**（机器 JSON 污染、引用覆盖率不足、材料性论断不可追溯、必需章节缺失、关键矛盾未解决等——纯代码检测，不经过模型，全部定级 Critical）。无论来源，全部经过同一套规范化进入 Issue Ledger。

### 3.2 语义身份与去重

每条 Issue 的身份 `issueKey` 由「缺陷类型 + 领域 + 受影响目标」哈希得出，与哪个评审者发现、用什么措辞、在第几轮无关。六路审核重复发现同一缺陷时自动合并为一条（严重度取最高），并保留全部来源记录——解决了「一个缺陷生成六个修复任务」和「换个说法就算新问题」两类失真。

### 3.3 负责人路由：模型说了不算

Issue 的修复负责人（data / industry / company / report）由服务端根据证据路径、检查项前缀、评审视角**推导**，模型给出的 owner 与推导不一致时直接报错。纯表达/结构类问题强制路由给 report（重新成稿），不会错发给上游分析师。多个来源对负责人有分歧的 Issue 标记为不可路由，宁可搁置也不乱修。

### 3.4 修复包：防伪造的执行授权

同一负责人每轮只收到**一份**合并修复包（Repair Packet），包含全部待修 Issue、按严重度排序的指令、约束和逐条验收标准。两个关键安全设计：

- **包内容是纯服务端投影**——模型写的描述、实体名、检查项 ID 等一律替换为服务端计算的确定性摘要和授权 token，固定指令文本由服务端生成。模型输出的自然语言**永远不能成为执行授权**（这是对提示注入攻击的结构性防御，而不是靠关键词过滤）。
- **执行器独立重算**——WorkflowExecutor 在路由前从 Ledger 重新计算修复包的每个字段，伪造一个格式正确的 token 也无法通过，因为它必须等于从 Issue 推导出的确定性投影。

### 3.5 关闭标准：复检者主导，修复者不能自证

Issue 生命周期为 `open → assigned → addressed → resolved`（另有 minor 默认 `deferred`、复发标 `regressed`）。负责人完成修复后 Issue 只能进入 `addressed`；**只有全部指定复检者在新一版 Draft 上给出带证据的 resolved 结论，Issue 才关闭**。复检者集合按来源限定：Reviewer 发现的问题需要六路全部确认；Scoreboard 发现的问题需要三个 Reviewer 加上它自己的来源 Scoreboard（无关 Scoreboard 不能卡住关闭）；确定性门禁的问题由门禁自己复检。已解决的问题再次出现标 `regressed`，不能伪装成新的低严重度问题。

### 3.6 为什么重要

这套系统把「报告质量」从主观印象变成一本可审计的账：每条缺陷有身份、有证据、有负责人、有修复历史、有独立复检记录；修复不再是往 prompt 里塞意见，而是有验收标准的闭环任务。审核者、修复者、复检者三权分离，任何一方都无法单独宣布质量合格。

## 4. 核心贡献二：Scoreboard——内容质量的量化审计

代码主体：`backend/src/domains/research/scorecards/`（catalog / core / issues / projection，约 1,560 行）+ 三个新 Agent 定义。

### 4.1 固定量表，机械算分

三个 Scoreboard Evaluator 按 v3.1 量表逐项评分：Data 24 项、Industry 24 项、Company 28 项，每项固定权重（程序强制权重合计恰好 100）、0–4 整数评分。总分、上限（cap）、质量等级（A ≥90 / B ≥80 / C ≥70 / D ≥60 / F）全部由程序用整数基点算术计算——**Agent 只能逐项打分和给证据，不能自己填总分**。评分单元防止压扁：Data 全项目一个单元，Industry 按重要行业分单元（按重要性加权聚合，缺失重要行业自动触发上限），Company 按每个 ticker 独立评分、不制造无法解释的全项目均分。

### 4.2 分数只展示，Issue 才路由

这是整个设计里最重要的决策：**总分、等级、通过与否只用于质量展示，不直接触发任何返工或拦截**。低分必须落成具体 Issue 才能进入修复闭环，而这座桥是硬规则、双向校验的：

- 评分 ≤2 的项**必须**产生 Major 或 Critical Issue，否则 evaluator 输出整体无效（fail closed）；
- 评分 3 只有存在明确可修复缺口时才允许 Minor；评分 4 **必须没有** Issue；
- 每个被触发的 cap 必须有对应的 Major/Critical Issue；
- Critical 升级需要证据门槛：只有固定 Critical cap 生效，或有「原始来源核对为矛盾」的记录配合捏造/重大事实错误标签时才允许。

这样既拿到了量化审计依据，又避免了「总分低于 80 就返工」这类伪精确的阈值治理——分数波动不会绑架流程，具体缺陷才会。

### 4.3 确定性质量审计（Scoreboard 之外的硬底线）

与模型评分并行，每轮还有一套纯代码的报告质量审计：9 项布尔检查，包括正文无机器 JSON 污染（732 行的专用检测器，覆盖各种代码栅栏、HTML 包装、拼接与深层嵌套的绕过方式）、材料性论断引用覆盖率 ≥95%、可追溯率 = 100%、必需章节齐全、无未解决关键矛盾。任何一项不过即产生 Critical Issue。这保证了不管模型评审表现如何，底线由确定性代码兜住。

### 4.4 live 运行的实证

真实 Daily One 中三个 Scoreboard 打出 37.5 / 42.5 / 30.25 分（均为 F 级），但 Issue Ledger 中 0 个 Critical——报告照常交付并 `decisionReady=true`，同时三个 F 级分数完整展示给用户。这正是设计意图的实证：分数忠实汇报质量现状，但不越权拦截交付；反过来，这组数字也明确告诉我们内容质量还有多大差距（见第 10 节卡点）。

## 5. 三层产品状态：报告永不消失，决策严格把关

- `reportAvailable`：存在完整、digest 校验通过的报告即为 true——**与 Conclusion 成败、Issue 多少无关**；
- `qualityStatus`：仅由未解决 Issue 严重度决定——无 Issue 为 passed，只有 Major/Minor 为 with-issues，存在 Critical 为 failed；
- `decisionReady`：有效报告 + 0 个未解决 Critical + 来源一致的 Conclusion，三者齐备才允许 Decision/Portfolio 消费。

配套机制：`latestUsableDraftRef` 保证只要生成过完整 Draft，无论后续修复失败还是运行中断，最新可读版本始终可查（降级状态下强制 `decisionReady=false`）；Conclusion 失败或与报告 digest 不符时，报告照常展示、结构化评级明确标注不可用，绝不伪造兜底评级；Human Review / waive / bypass 从活跃链路整体退役（净删约 2,000 行），历史记录只读保留。

## 6. 工程加固：47 个修复提交做了什么

奠基提交之后的加固工作按问题类型分五类（举代表提交）：

1. **模型输出鲁棒性**（`20bae37`、`745e8e5`、`c7dbc81` 等十余个）：live 模型返回的审核结果经常有包裹、字符串化、字段缺失等畸形。统一原则是**保守恢复**——能精确解析的部分恢复，恢复不了的一律标为「未评估」而非「通过」；漏报的覆盖检查会被合成为待查项，模型漏挂的缺陷会被合成为 Issue。宁可多报问题，不静默放行。
2. **运行时稳定**（`a4306cb`、`d5f74d6`、`4e1aec8`、`724de17` 等）：本地网关承受不了六路并发流式调用——引入 token 预约队列、全局并发上限（评审节点串行化）、有界重试预算（API 重试与节点重试分开计数）、瞬时错误分类，让 70 分钟的 live 长跑稳定完成。
3. **上下文预算**（`78b21fb`、`7be78f9`、`fdc2c12`）：跨轮复检上下文原本无界增长（递归历史、重复指令）。改为固定字段白名单投影 + 硬截断上限，六个评审者验证过可容纳 62 条 Issue 的复检上下文。
4. **正文安全与评级一致性**（`a3a8fd3`、`adb76db`、`88f6ce5`、`bf887eb`）：机器 JSON 检测的对抗性覆盖、报告与 Conclusion 评级冲突检测、live 评分输出的完整规范化、QA 扫描器误报修复。
5. **路由与关闭精度**（`e315b5e`、`e6480cb`、`16a2df6`、`d002706`、`30fc41b`）：负责人从证据路径推导、表达类问题不再错发上游、复检者按来源限定、确定性门禁获得自我复检能力。

这些不是零散补丁：每一个都对应 live 环境实测暴露的一类失败，且几乎每个都带着对抗性回归测试。

**第三级：产品面浏览器验收**。用真实 Chromium 在桌面（1440×1000）和移动（390×844）视口完整点击验证列表 → 详情 → 报告链路。这次真实验收发现了两个此前声称已完成的 UI 里的真缺陷（展开 88 条 Issue 把报告阅读器压到 0 高度；Issue 行显示哈希而非人话描述），当场修复并回归通过——也侧面说明「真实验收」和「测试通过」之间确实有距离。

## 9. 为什么这些改变重要

1. **「报告质量」第一次有了机器可验证的定义**。审核的、发布的、提取结论的是同一份字节（digest 链闭合）；质量结论来自可重放的账本而非某个模型某次的语气。这是把研究产品当成可信交付物的前提。
2. **质量问题从「感觉」变成「账」**。87 个 Major 不再是一句「报告还不够好」，而是 87 条有证据、有负责人、有修复历史、有复检记录的具体缺陷——管理层可以据此决定投入，而不是凭印象。
3. **这是规模化的前提**。Daily 100 意味着每天 100 份报告，人工 Review 在这个量级上不存在。本分支把质量把关从「有没有人看」变成「闭环有没有跑完」，且已在真实调度入口证明端到端可行。
4. **成本可控且有账可查**。token 硬顶在模型调用前生效，重试有界，live 授权单次使用且绑定精确提交——541 万 token 的单报告成本是精确测量值，不是估计。
5. **安全边界是结构性的**。模型输出在任何位置都不能成为执行权威（修复包去语义化 + 执行器独立重算），提示注入在这条链上没有落点；所有历史工件不可变，事后审计随时可做。

## 10. 当前卡点

按影响排序：

1. **未合并、未部署**。全部工作在隔离分支/worktree 完成，生产端口（8787）仍在跑旧链路。合并、推送、部署、生产 systemd timer 更新均需另行授权——这是当前到产品价值之间最直接的一步。
2. **live 样本量 n=1**。确定性门禁覆盖很全，但真实模型下只跑过一次 Daily One。Daily 100 的稳定性、成本分布、失败模式都未证明；QA-01 / Gate E 的完整关闭是独立工作。下一步需要一个小批量 live 授权（如 Daily 10）来积累分布数据。
3. **质量校准是下一场硬仗**。live 运行的三个 F 级评分和 87 个 open Major 说明：交付门槛过了，内容质量还不高。三个具体问题：两轮修复上限内 Major 消不完（且 Minor 默认永不修复）；保守恢复启发式会合成 Major Issue，可能系统性推高计数；评分严格度与 Issue 严重度映射还没有经过多样本校准。需要定义「Major 数量收敛」的目标曲线，而不只是「0 Critical」。
4. **成本与延迟**。单报告 541 万 token、约 70 分钟（六路审核 + 满额两轮修复）。线性放大到 Daily 100 约 5.4 亿 token/天，不可行。需要分级审核强度（如首轮全量、复检定向）、按 Idea 质量抽样深审、或修复轮内的增量审核。
5. **闭环自身的结构性限制**（有意的取舍，但要知道在哪）：负责人冲突的 Issue 会进入不可路由状态，只记录不修复；两轮耗尽后没有升级路径（Human Review 已退役，Critical 耗尽即 quality-failed）；六路审核必须全部产出有效结果，任何一路失败整个节点重试，没有 5/6 降级模式；修复包去语义化后，修复 Agent 拿到的上下文较少，可能影响修复命中率。
6. **遗留清理**。少量旧代码已无生产引用但仍在库中（旧 adjudicator、一个未被使用的并行聚合实现等），应在合并前后清理，避免双轨误用。

## 11. 建议的下一步

1. 合并评审 + 生产部署授权（本分支 → main → 部署），让新闭环真正接管每日生产；
2. 小批量 live（Daily 10 量级）授权，校准 Issue 严重度映射与 Scoreboard 严格度，建立 Major 收敛基线；
