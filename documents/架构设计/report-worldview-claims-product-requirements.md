## 0. 这套系统在解决什么问题

系统的目标是把「读研究报告」变成一条可积累、可验证、可自我改进的投资信号生产线，而不是每次读完报告就丢掉。整条链路由两个循环组成：

**主循环（从报告到投资想法）**：系统持续吸收外部与内部研究报告，把报告中的观点消化进一份自己维护的世界观文档（Worldview）；再基于「报告 + 当前世界观」提炼投资逻辑（Opportunity），把逻辑映射到具体股票上做基础核验，最后用天梯排序（ELO / Deal Ladder）从候选股票中筛出投资 Idea。

**验证循环（从判断到自我改进）**：报告中的结论会被拆成一条条可验证的判断（Claim）。一个独立的每日系统（Side System）持续检查这些判断的对错，并且不只看结果对不对，还要检查当初讲的因果链是否真的成立。检查结果（Reflection）回流到两处：强化或削弱 Worldview 中的观点；以及作为 Analyzer Reviewer 的上下文，提醒后续分析避免重复同类错误。

一句话：**主循环负责产生投资想法，验证循环负责让系统越来越不容易自欺**。

### 0.1 术语表

| 术语 | 含义 |
|---|---|
| 报告库 | 所有研究报告的存储与索引。外部报告（券商、研究机构等）与内部报告（FinAgent 自己生成的）物理隔离，但共用一套索引。 |
| Worldview | 系统自己维护的世界观文档 `worldview.md`（英文 Markdown）。不是报告摘要，而是系统消化所有材料后形成的「自主观点 + 市场观点地图 + 证据」。 |
| base view / House View | Worldview 中系统自己选定的基准判断（base case）：当前最相信哪个叙事、为什么、置信度多高、什么信号会改变它。 |
| Contribution | 报告初读的产物：这篇报告相对当前 Worldview 带来了哪些新增观点、支持证据或冲突证据。是 Worldview Review 的输入。 |
| 初读 / 复读 | 初读：报告首次进入时，对照完整 Worldview 判断它带来了什么新东西（产出 Contribution）。复读：Worldview 完成本轮更新后，带着更新后的 Worldview 再读报告，产出 Opportunity 和 Claims。 |
| Worldview Reviewer | 负责决定 Worldview 是否更新、如何更新的 LLM 角色，输出 KEEP / REVISE / ADD / SPLIT / RETIRE 五种语义动作。 |
| Opportunity | 一条投资逻辑（thesis），例如「存储供给受限将推动涨价周期」。它不是某只股票；一条逻辑可以映射到多只候选股票。 |
| BasicCompanySnapshot | 对一只候选股票的单段式快速摘要（不超过 1000 字），由基础查询 + AI Search 拼接，用于回答「这家公司是谁、靠什么赚钱、和这条逻辑到底有没有关系」。 |
| StockFit | 对「股票 × Opportunity」适配度的判断：资料是否完整、业务暴露是否真实、财务估值有无红旗，决定股票进入 long_candidate、watch/unverified 还是 reject。 |
| Deal Ladder / ELO | 候选股票的天梯排序机制。不让 LLM 一次性拍脑袋选十只，而是分组做相对比较，用 Glicko-1 评分系统累积出稳定排名。 |
| Glicko-1 | 一种带不确定度的 ELO 变体。每个候选有评分 R（相对竞争力）和不确定度 RD（对 R 的信心）；比较数据越多 RD 越小。 |
| R − 2×RD | 保守评分：从评分里扣掉两倍不确定度再排序，防止「只赢过一次的高不确定候选」冲到榜首。 |
| degraded | 排序过程中某次 LLM 比较失败、使用了回退顺序的标记。必须对用户可见。 |
| Claim | 从报告结论拆出的一条可验证判断，带验证窗口、指标、阈值、因果链和失效条件。不是「看涨/看跌」的方向猜测。 |
| verificationWindow / verificationInterval | 验证窗口：这条判断在什么时间段内接受检验（startAt–endAt）。验证间隔：窗口内多久做一次深度取证（日/周/月）。 |
| causalSteps | 因果链的分步拆解：每一步的中间信号和预期时滞。验证时逐步核对，而不是只看最终涨跌。 |
| invalidation | 失效条件：出现哪些事实即可判定这条判断已经错了。 |
| ClaimObservation | 一次验证的记录（证据、逐步核对结果、结论）。只能追加，原 Claim 不可改写。 |
| Side System | 与主报告分析解耦、独立运行的每日验证系统：每天扫描处于验证窗口内的 Claims，按间隔做深度验证。 |
| Reflection | 对验证结果的复盘：不止判断对错，还要回答因果链哪一步断了、方向对是不是碰巧、错误最早暴露在哪个信号。 |
| Analyzer Reviewer | 对分析环节的评审角色。接收 Reflection 输出作为上下文，指出分析盲点与归因错误；只影响后续评审上下文，不自动修改 Prompt。 |
| Context Manager | 控制每次 LLM 调用装什么进上下文的组件。核心规则：Worldview 必须完整装载，预算不够时缩小报告分块，绝不静默截断 Worldview。 |
| Compaction | Worldview 接近体积上限时的受控压缩：一次版本化的 LLM 编辑任务，去重压缩但不得丢观点、反证和失效条件。 |
| digest / coverage / lineage | digest：内容指纹，用于判定「同一份内容」并追溯输入。coverage：哪些报告已被哪个 Worldview 版本消化过。lineage：版本谱系，每个版本由哪个前版本 + 哪些输入演化而来。 |
| 失败关闭（fail-closed） | 前置条件不满足时宁可停止并显式报错，也不静默降级继续跑。 |

## 1. 产品主链

主链按顺序是：

1. **报告库**持续收录外部与内部报告，完成提取和索引；
2. 每篇新报告经过**初读**，判断它对当前 **Worldview** 带来什么新增或冲突（Contribution），驱动 Worldview 的评审与更新；
3. 基于「报告 + 更新后的 Worldview」做**复读**，提炼出一个或多个 **Opportunity**（投资逻辑），并映射到多只候选股票；
4. 每只候选股票做**基础核验**（BasicCompanySnapshot + StockFit），资料不足或逻辑不成立的被拦下；
5. 通过核验的股票（去重后最多 30 只）进入 **Deal Ladder / ELO** 天梯排序，产出**投资 Idea 初筛**结果。

与主链并行的是验证回路：

6. 复读同时把报告结论拆成可验证的 **Claims**；
7. **Side System** 每天扫描处于验证窗口的 Claims，按间隔做深度验证，形成 Observation；
8. 验证结果经 **Reflection** 复盘后，一方面**强化或削弱 Worldview 的观点**（必要时触发 Worldview Review），另一方面进入 **Analyzer Reviewer** 的上下文，改进后续分析。

规模口径：30 篇外部报告只是初期测试样本，正式报告库持续扩展；「最多 30 个」仅指进入 ELO 比较环节的股票候选数。

### 1.1 复读是分叉点：一次阅读，两种产物

复读是主链上最重要的分叉点。同一次「完整 resulting Worldview + 报告」的阅读，产出两种性质完全不同的东西——Opportunity 面向**行动**，Claim 面向**验证**。

**Opportunity 怎么得出**：复读时模型带着更新后的 Worldview 问第一个问题——「这篇报告结合我现在的世界观，指向什么可操作的投资逻辑？」答案落成一个或多个 Opportunity：每个写清逻辑本身、受益环节、投资期限和主要风险，然后映射候选股票，进入第 4 节的核验与排序流水线。Opportunity 的价值在于**当下**：它要在本轮分析里被消化成候选股票和投资 Idea。

**Claim 怎么得出**：同一次复读中模型再问第二个问题——「这篇报告的关键结论（包括支撑上述投资逻辑的结论），哪些是将来可以被数据检验的判断？」这些结论按对象、时间和因果步骤拆成一条条 Claim（第 5 节），过可验证性门禁后进入 Claim Store。Claim 的价值在于**将来**：它是系统提前立下的字据，等着被市场验证。

打个比方：Opportunity 是「我打算怎么下注」，Claim 是「我预先写下的、事后可以对答案的判断依据」。前者驱动决策，后者驱动学习。

### 1.2 Opportunity 与 Claim 的关系

**同源，不同向**。两者出自同一次复读、依据同一批报告结论和同一版 Worldview。Opportunity 是这批结论的行动面（能不能变成可买的候选），Claim 是同一批结论的可证伪面（将来怎么对答案）。

**多对多，而非一一对应**。一个 Opportunity 的 thesis 通常拆出多条 Claim——典型如产业、公司、交易三层（见 5.1 的存储涨价例子）；反过来，也存在不挂任何 Opportunity 的 Claim，例如报告里值得跟踪但暂时推不出可操作逻辑的宏观判断。两者不互相引用对方的 ID，而是通过共享的标的和证据关联：Claim 用 `linkedTickers` 挂到可能受影响的股票，证据引用则作为报告侧元数据保存。

**生命周期完全不同**。Opportunity 短命：在一个分析批次内走完提炼 → 映射 → 核验 → 排序，结果沉淀为候选池和 Idea 初筛。Claim 长命：出生后要活过整个 `verificationWindow`（数周到数月），期间被 Side System 每天扫描、按间隔深度验证，最后以 confirmed / refuted / partial / inconclusive / expired 之一收场。

**反馈是间接的，刻意绕经 Worldview**。Claim 被证伪不会直接改写任何已有 Opportunity 的结论或候选池排名；它先经 Reflection 写入 Worldview Reinforcement（削弱相关观点、记录断裂的因果链），再在**下一次**复读时影响系统产出什么样的 Opportunity。这个间接性是有意设计：单条 Claim 的对错噪音很大，直接联动会造成「一条判断翻车就机械推翻整个机会」的过拟合；让证据先在 Worldview 层汇总、权衡，反馈才是稳健的。

### 1.3 后续会不会成为两个子系统？

会。目标架构里它们分别是两条下游流水线的入口，运行节奏、触发方式和产出都不同：

| | 决策子系统（Opportunity 驱动） | 验证子系统（Claim 驱动） |
|---|---|---|
| 触发方式 | 事件触发：新报告完成复读时运行 | 时钟触发：每天定时运行，与有无新报告无关 |
| 链路 | Opportunity → 股票映射 → Snapshot / StockFit → 候选池 → Deal Ladder → Idea 初筛 | Claim Store → 每日扫描 → 深度验证 → Observation → Reflection → 回流 |
| 回答的问题 | 现在能做什么 | 我们过去的判断质量如何 |
| 对应章节 | 第 4 节 | 第 5、6 节 |

两个子系统**不直接调用对方**。耦合点只有两处：Worldview（验证子系统把经验写进去，决策子系统在下一次复读时读到）和 Analyzer Reviewer 上下文（验证子系统提炼的分析教训，供后续分析评审时参考）。这种松耦合保证了任何一边故障或暂停，另一边照常运行——Side System「与主报告分析解耦，独立运行」（第 6 节）说的就是这件事。

## 2. 报告索引：来源隔离，内容多标签

**报告分两个物理区**。外部报告区存放券商、研究机构、行业材料，持续新增；内部报告区只存放 FinAgent 自己生成且状态为 verified final 的报告。两区共用一套统一报告索引，但原文按来源物理隔离，避免内部生成内容混入外部素材（或反之）后无法追责。

**索引上只有两类严格边界**：

- 来源：`external / internal`；
- 提取状态：`ready / needs-ocr / failed`。只有 `ready` 的报告进入下游分析；需要 OCR 或提取失败的报告停在报告池外，不参与任何后续环节。

**内容分类一律用多选标签 `categoryTags[]`，不做强制单一归类**。可选标签包括：宏观、策略、主题、事件、产业、公司深度，并允许扩展。同一篇报告可以同时是「主题 + 事件 + 产业 + 公司深度」——例如一篇讲存储涨价的报告，既是主题研究，也覆盖行业事件和具体公司。除内容标签外，索引还挂时间、地域、资产类别、行业、Ticker、来源等检索元数据。

之所以这样设计：来源和提取状态影响数据可信度与可用性，必须硬性隔离；而内容分类只是检索手段，强行单选会丢信息。

初期 30 篇测试样本清单计划落在 `backend/scripts/support/external-report-sample.v1.json`（该文件尚未创建）。

## 3. Worldview 应该怎么写

### 3.1 稳定外框，内部允许柔性变化

Worldview 的 canonical 产物是一个英文 Markdown 文档 `worldview.md`。它**不是报告摘要，也不是固定打分表**：它是系统消化全部材料后写下的「自己怎么看世界」，外层结构稳定，内部由 LLM 根据材料自由增删、合并或拆分子主题。

体积上尽量控制在 100k tokens 以内。100k 是软上限，不是鼓励写满的目标；接近上限时应先做受控压缩（见 3.4 的 Compaction），旧版本继续归档保留。

文档固定分八个大块，每块的职责如下：

1. **自主观点 / House View** — 系统当前的 base case：最相信哪个叙事、理由是什么、置信度多高。这是整份文档的「结论区」。
2. **宏观与市场状态** — 增长、通胀、政策、流动性、风险偏好的当前读数与趋势。偏事实层，为后面的观点提供背景。
3. **主题与产业链** — 关键结构性趋势（例如 AI 资本开支、存储涨价周期），每条写清传导路径、受益环节和受损环节。
4. **市场观点地图** — 市场上并存的不同流派观点：谁在说什么、各自的逻辑、依据的证据、隐含的结果。这一块只负责如实呈现分歧，不做裁决。
5. **证据与反证** — 支持证据、冲突证据和明确的未知项。专门防止系统只收集对自己有利的证据。
6. **投资含义** — 从前五块推出的配置方向、机会与风险，以及「什么条件下不行动」。
7. **观察信号** — 一组可观察指标：出现什么信号应触发 Worldview 更新、宣告某观点失效、或切换到另一个场景。
8. **Claim Reflection Reinforcement** — 由每日验证回流的记忆：哪些历史判断被强化、哪些被削弱、失败出在结果还是因果链、哪些来源被证明可靠或不可靠。

八个大块相对稳定；每块内部的子标题、篇幅和观点数量由 LLM 根据材料柔性决定。

### 3.2 Worldview 的写作原则

- 先区分四种东西：**事实**（可查证的数据）、**外部观点**（别人怎么说）、**系统推断**（系统从材料推出的中间结论）、**最终自主观点**（系统选定的 base view）。混在一起写是最常见的失败模式。
- 吸纳不同观点，但不能简单平均。「一半人看多一半人看空，所以中性」是无效结论；必须写清每种观点背后的逻辑和证据强度。
- 必须形成自己的 base view，并说明为什么暂时选择它、置信度多高、什么信号会改变它。不允许只罗列观点不下判断。
- 少数派观点和反证不删除，进入「市场观点地图」和「证据与反证」保存。今天的少数派可能是明天的 base view。
- 「Claim Reflection Reinforcement」必须单独成块，记录历史判断哪些被强化、哪些被削弱，以及错在结果还是因果链。
- 顶层八块相对稳定，内部结构柔性。

### 3.3 Worldview 怎样 review 和更新

**输入**：Worldview Review 由四类材料共同驱动——

1. 新报告初读产出的 Contributions（新增/冲突观点及证据）；
2. 上一版完整 Worldview；
3. Claim 验证的对错与因果链 Reflection（来自第 6 节的 Side System）；
4. 既有 Analyzer Reviewer 的反馈。

**过程**：LLM Worldview Reviewer 拿到这四类输入后，先做观点比对——识别哪些是新增观点、哪些与现有内容重复、哪些与现有观点冲突、哪些现有观点已被新材料证伪或过时。然后对每处比对结果选择一个**语义动作**：

- **KEEP** — 新材料已被现有 Worldview 覆盖，不改文档。只记录本次 review 和 coverage（证明这篇报告确实被看过、被判定为无新增）。
- **REVISE** — 修改某条既有自主观点或其置信度。适用于方向不变但强度/条件变了，或需要方向性修正的情况。
- **ADD** — 吸纳一个新的并行观点（新主题、新流派），与既有观点不冲突。
- **SPLIT** — 把一个观点拆成多个场景或流派。适用于证据显示单一叙事不再成立、市场分化成几条路径的情况。
- **RETIRE** — 宣告某观点失效退役。不删除文本，标记失效原因并保留历史。

**输出**：KEEP 不产生新版本；REVISE / ADD / SPLIT / RETIRE 任一发生则生成 Worldview v+1，旧版本归档。

**职责边界**：是否更新、怎么改，由 LLM 根据观点的新颖性、证据强度、冲突程度和投资影响做柔性判断，**不使用僵硬的固定分数阈值**（例如「新颖度 > 0.7 才更新」这类规则）。确定性代码不参与内容判断，只负责过程可追溯：记录 digest、维护 coverage、管理版本号和 lineage。

### 3.4 体积控制：Compaction

3.1 说过 `worldview.md` 的软上限是 100k tokens。逼近上限时，系统单独触发一次**受控压缩（Compaction）**，而不是放任文档膨胀、或在使用时偷偷截断。

Compaction 是一次版本化的 LLM 编辑任务——和 3.3 的 REVISE 等动作一样，它产生 Worldview v+1，旧版本归档。它只做两件事：去重、压缩表述。硬性红线是不得丢失：不同观点（含少数派）、关键证据引用、失效条件、Claim Reflection 内容。压缩期间暂停初读/复读，完成后再恢复。

### 3.5 Context Manager：每次调用装什么

主链上有三类 LLM 调用需要读 Worldview：报告初读、Worldview review、报告复读。Context Manager 负责决定这些调用的上下文构成。每次调用的上下文固定四部分：**完整 Worldview、报告 metadata / tags / digest、当前报告分块（chunk）、任务 Prompt 与输出 schema**。围绕它只有三条规则：

**规则一：Worldview 整篇装载，不用摘要。** 摘要会丢失少数派观点、反证和失效条件，而这些恰恰是判断「新报告有没有带来新东西」时最需要的参照。装哪个版本取决于调用类型：初读和 Worldview review 装 current 版本；复读装本轮更新后的 resulting 版本（两次阅读的分工见 1.1）。

**规则二：超预算时牺牲 chunk，不牺牲 Worldview。** 四部分装不下模型上下文时，缩小报告 chunk（增加分块次数），循环直到装得下。绝不截断 Worldview。

**规则三：仍装不下就显式处理，不静默降级。** chunk 已缩到最小仍超预算，说明 Worldview 本身过大——先执行 3.4 的 Compaction 再继续；不可行则失败关闭（报错停止）。任何情况下都禁止悄悄换成摘要或截断尾部。

**审计**：每次调用记录 `worldviewId`、Worldview token 数、report chunk 范围和 context digest，保证事后能精确还原「模型当时看到了什么」。

## 4. Opportunity：一个逻辑可以对应多只股票

Opportunity 是**投资逻辑，不是 ticker**。一次报告复读可以形成一个或多个 Opportunity；每个 Opportunity 可以关联多只候选股票。这样设计是为了避免「报告推荐了 A 公司，系统就只看 A 公司」——同一条逻辑（比如存储涨价）往往有一串受益公司，报告未必都点名。

从报告到候选股票池的完整流程：

1. **提炼 Thesis**：基于报告和 current Worldview，提炼 Opportunity 的投资逻辑——讲清逻辑本身、受益环节、投资期限和主要风险。
2. **映射候选股票**：为每个 Opportunity 列出候选股票，来源既包括报告明确提及的公司，也包括产业链上相关的公司。
3. **实体与 Ticker 校验**（确定性环节）：确认每个候选的公司实体、上市地和证券身份，防止同名混淆、退市股或错误 ticker 进入后续分析。
4. **BasicCompanySnapshot**：为每只通过校验的股票生成一段基础公司快照（详见 4.1）。
5. **四维评估**：基于快照评估——业务与 Opportunity 的真实暴露（这家公司真的受益于这条逻辑吗，受益占它业务的比重多大）；收入、利润、现金流、资产负债的基本状态；基础估值、流动性和数据时点；治理、稀释、周期性和重大风险。
6. **StockFit 门禁**：综合四维评估回答三个问题——基本资料完整吗？逻辑暴露真实吗？财务与估值有明显红旗吗？结果三选一：
   - 资料不足 / 证券身份不清 / 无法证明真实受益 → `unverified / watch`，**不得进入 long candidate**；
   - 资料齐但逻辑不匹配或有严重红旗 → `reject`；
   - 通过 → `long_candidate`。
7. **逐股票评分**：对每只 long_candidate 按机会质量、公司质量和赔率打分。
8. **按 Ticker 去重**：同一只股票可能被多个 Opportunity 映射到，去重后保留。
9. **进入候选池**：最多 30 只股票，交给 Deal Ladder / ELO 排序。

### 4.1 BasicCompanySnapshot 的形态

BasicCompanySnapshot 是**一段公司摘要，不是表格，也不是一份新的公司深度报告**。系统用基础 company query、财务查询和 AI Search 快速拼接，正文控制在 1000 字以内。

这一段话应自然覆盖：公司与 Ticker 身份、主营业务和收入来源、与 Opportunity 的真实业务暴露、近期收入/利润/现金流和资产负债的基本状态、一个适用的基础估值视角、流动性，以及最重要的风险或红旗。`asOf`（数据时点）、查询来源和 evidence refs 作为段落外的轻量元数据保存。

没有足够资料、证券身份不清、或无法证明公司确实受益时，只能进入 `watch/unverified`。这条规则专门防止一类常见错误：**主题是对的，但映射出的公司完全没研究过**。

### 4.2 ELO / Deal Ladder 怎样工作

**为什么不让 LLM 直接选十只**：一次性从 30 只里挑 10 只，模型没有可比性参照，赔率和证伪信息全部丢失，结果接近拍脑袋。天梯赛的思路是：每次只让模型对一小组（5 只）做相对排名——这是模型擅长的任务——再用评分系统把多轮小组赛的结果累积成全局排名。

**比较的标准**是同一投资期限下「风险调整后的赚钱确定性 + 赔率」。

**核心概念**：

- `R`：相对竞争力评分，初始 1500，赢比较涨、输比较跌；
- `RD`：评分不确定度，初始 350。比较数据越多 RD 越小（后续保持在 30–350 之间），表示「对这个评分有多确定」；
- `R − 2×RD`：保守评分，最终排序依据。从评分里扣掉两倍不确定度，使「只靠一次偶然胜出、证据还很少」的候选无法冲到榜首——宁可低估，不可高估。

**初始评分（播种）**：每只候选不从零开始，而是用已有先验播种：

- 基准 1500 分；
- 推荐分调整：`(recommendationScore / 100 − 0.5) × 500`，即推荐分 100 加 250 分、推荐分 0 减 250 分；缺少 recommendationScore 时退化使用 confidence；
- 赔率凸性加成：skew（上行空间 / |下行空间|）越高加分越多，skew = 1（对称赔率）不加分，约 skew = 3 到达满加成，再高封顶；加成幅度受 mandate 的 convexityBonus 参数调节；
- 期望收益调整：`clamp(expectedReturnPct / 40, −1, 1) × 120`，期望收益 ±40% 时达到 ±120 分的上限；
- 初始 RD 统一为 350（先验只影响起点评分，不影响不确定度）。

**排序流程**：

1. **去重与短路**：按 ticker 去重。候选 ≤ 2 只时不调用 LLM，直接按播种后的保守分排序输出。
2. **粗筛阶段（多轮小组赛）**：候选 ≤ 8 只跑 2 轮，否则 3 轮。每轮：
   - 按当前保守分 `R − 2×RD` 排序，然后按轮次做**错位旋转分组**，5 只一组（落单的 1 只并入上一组）。错位保证不同轮遇到不同对手——强者也会碰到中游，避免「强碰强、弱碰弱、跨档永远没比过」；
   - LLM 对组内候选做相对排名（best → worst）。它看到每只候选的期限、thesis、公司摘要、赔率（期望收益 / skew / 上下行）、关键因子（PE、ROE、增长、动量等）和失效条件，并给出比较理由；
   - 组内名次展开成**两两对局**：排名靠前者胜排名靠后者；
   - 一轮结束后统一做 **Glicko-1 更新**：用本轮开始前的 R/RD 快照计算所有对局，再一次性写回新的 R 和 RD。对手 RD 越高（信息越不确定），该场胜负对自己评分的影响越小。组间比较可以并发，但必须等一轮全部结束才更新，避免更新顺序影响结果。
3. **决赛圈**：粗筛结束后按保守分取 topN 进入决赛，N 默认取 mandate.maxHoldings 或 10。
4. **精排阶段**：决赛选手 ≤ 5 只跑 1 轮，否则 2 轮，流程同粗筛（分组 → LLM 排名 → 成对胜负 → Glicko-1 更新），目的是进一步收窄 RD、确定最终次序。
5. **输出**：按最终保守分排序，每只候选带 `ladderRank`（名次）、`R`、`RD`、`R − 2×RD`（保守分）、`compareNote`（最近一次有效组内比较中模型给出的理由）。

**失败回退（degraded）**：任何一次组内 LLM 排名失败或输出无效时，该组沿用回退顺序（组内按当前保守分的既有顺序），照常参与成对胜负和评分更新，但必须标记 `degraded` 并记录 reason，**对用户可见**——用户有权知道某个排名有多少成分来自模型失败时的默认顺序。

## 5. Claim：不是猜方向，而是可验证的因果判断

### 5.1 从结论拆成可验证 Claim

Claim 的拆分发生在复读阶段，与 Opportunity 提炼同批完成（见 1.1）。报告的结论通常是一句压缩过的话，例如「存储涨价将改善相关公司盈利」。这句话没法直接验证——对象是谁？什么时候？涨价到盈利中间发生什么？所以要**按对象、时间和因果步骤拆分**成多条独立可验证的 Claim：

- **产业 Claim**（对象是产业指标）：供给约束将推动 NAND ASP 上升——可以用合约价数据验证；
- **公司 Claim**（对象是公司财务）：ASP 上升将改善某公司毛利率——可以用财报验证；
- **交易 Claim**（对象是市场价格与预期）：盈利预期上修将形成价格催化——可以用一致预期修正和股价验证。

三条 Claim 各自有独立的验证窗口、指标和数据源；产业对了但公司没受益、公司受益但市场早已 price in，这些差异只有拆开才看得见。

拆出的每条 Claim 按 Claim v2 结构成形，然后过**可验证性门禁**：

- 有数据源、时间窗、阈值，且有可观察的中间信号 → 进入 Claim Store；
- 主要由随机事件主导、无可靠验证路径 → 拒绝，或改写成可验证形式后再进入。

门禁不排斥事件型 Claim（例如政策发布、产能投放），但事件必须有可观察的过程、前置信号或明确的结果来源。完全依赖不可预测随机事件、且无法观察中间机制的判断（例如「某公司可能被收购」而无任何可观察前兆）不能进入正式 Claim Store。

### 5.2 Claim v2 必备字段

只保留验证一条判断所必需的核心字段：

| 字段 | 含义 |
|---|---|
| `assertion` | 具体会发生什么，而不是只写涨跌 |
| `subject / linkedTickers` | 判断对象以及可能受影响的股票 |
| `verificationWindow` | `startAt` 与 `endAt`：判断在这个时间段内接受检验 |
| `verificationInterval` | 日、周或月；多久应形成一次深度 observation |
| `metric / baseline / target` | 用什么指标、从什么基线出发、达到什么条件算数 |
| `verificationSources` | 可实际取得的验证来源 |
| `causalNarrative` | 用一段话完整讲清原因、传导和结果 |
| `causalSteps[]` | 因果链逐步拆解：每一步的中间信号和预期时滞 |
| `invalidation` | 哪些事实会证明判断失效 |

早期草稿里还有 horizon 标签、二阶连锁反应（downstreamEffects）、外部随机因素（exogenousRisks）、证据引用（supportingEvidenceRefs）等字段，均移出必备集：期限可由验证窗口推出，连锁反应和外部风险在 `causalNarrative` 里带一句即可，证据引用归报告侧元数据。确有需要时再作为可选字段回补，不预先设计。

`causalNarrative` 示例：

> 云厂商资本开支上升会先推高服务器和存储采购，随后提高存储厂商产能利用率；在供给扩张滞后的情况下，库存下降和合约价上涨将改善毛利率，并在下一至两个财报期推动盈利预期上修。若新增产能提前释放或终端需求转弱，传导链在库存与价格环节失效。

注意这段话同时给出了传导路径（capex → 采购 → 利用率 → 库存/价格 → 毛利率 → 预期上修）和失效位置（库存与价格环节）——验证时就按这条链逐步核对。

## 6. Claim Side System：每天检查，按间隔深度验证

每日 Side System 与主报告分析**解耦，独立运行**——即使当天没有新报告进来，验证照常执行。

每天的流程：

1. **筛选**：Daily Claim Scheduler 找出当前处于 `verificationWindow` 内的所有 Claims；
2. **每日轻检查**：对每条活跃 Claim 检查状态、窗口和是否出现新证据。这一步成本很低，天天做；
3. **判断是否到期**：按该 Claim 的 `verificationInterval` 判断是否该做一次深度验证——
   - 未到期：记录 checked（无新 observation，或标记 no-new-evidence），今天到此为止；
   - 到期：进入深度验证；
4. **深度验证**：收集并标准化证据，然后**逐步检查 `causalSteps`**——每一步的中间信号有没有如期出现——而不是只看最终涨跌；
5. **给出结论（verdict）**，五种之一：
   - `confirmed`：判断成立；
   - `refuted`：判断被证伪；
   - `partial`：部分成立（例如产业环节对了、公司环节没兑现）；
   - `inconclusive`：证据不足，暂无法判断；
   - `expired`：验证窗口结束，条件未达成；
6. **追加 ClaimObservation**：验证记录以追加方式写入；**原 Claim 不可改写**——历史判断必须保持当初写下的样子，才谈得上诚实复盘；
7. **Reflection**：Claim Reflection Reviewer 对结果复盘（必须回答的问题见下），输出流向两处：
   - **Worldview Reinforcement**：强化或削弱相关观点、记录失败的因果链和来源可靠性。若对 Worldview 有实质影响，触发一次 LLM Worldview Review；影响不大则保留为强化记忆，等后续材料一起汇总；
   - **Analyzer Reviewer Context**：分析盲点、归因错误、下次应补的证据，进入后续分析的 Reviewer 上下文。注意这只是给评审者的参考材料，**不自动修改任何 Prompt**。

### Reflection 必须回答

- 最终结果是对、错、部分正确，还是暂时无法判断？
- 因果链哪一步得到支持，哪一步断裂？
- 方向正确是否只是碰巧，原始机制是否真的成立？
- 哪个前置信号最早暴露了错误？
- 是 Worldview 假设错、公司映射错、证据不足，还是时间窗口设错？
- 该结果应强化、削弱还是仅补充哪个 Worldview 观点？
- Analyzer Reviewer 下一次应要求补充什么证据或避免什么归因错误？

前三条针对「结果 vs 机制」——方向蒙对但机制不成立的判断不值得强化；后四条针对「错误归因」——只有定位到错在哪一层，反馈才能落到正确的地方。

## 7. 确定性系统与 LLM 的职责

分工的总原则：**凡是需要理解语义、权衡观点的交给 LLM；凡是涉及身份、时间、数据和状态的交给确定性代码**。LLM 的判断可以柔性，但过程必须可追溯、数据必须真实。

| 确定性系统负责 | LLM 负责 |
|---|---|
| Report/Claim/Worldview 身份、digest、版本和 lineage | 从报告中理解观点和因果逻辑 |
| 验证窗口、每日调度、verificationInterval | 将结论拆成可验证 Claims |
| 指标比较、数据时点、证据引用和状态机 | 权衡不同市场观点及其证据 |
| Opportunity 与股票实体校验、基础数据完整性 | 判断公司与 Opportunity 的业务相关性 |
| 不可变 Claim 与追加 Observation | 写 Worldview 自主观点和 Reflection |
| 失败关闭、人工 review 和审计 | 柔性 Keep/Revise/Add/Split/Retire |

两条硬约束：LLM 不能伪造基础财务数据（财务数字必须来自确定性查询）；也不能因为语言上「看起来合理」就绕过可验证性门禁。

## 8. 当前实现与目标模型的差距

本节按 2026-08-09 对代码库的实际核对改写（v4.0 原表描述的「当前 MVP」多处与代码不符，已订正）。

**已实现**的是一条与本 PRD 平行的流水线：`idea-generation` 工作流（来源发现 → 候选筛选 → idea 生成）、`run-analysis` 研究与报告生成工作流（含证据/引用审计与人工 review），以及 decision 域的 Deal Ladder（Glicko-1 天梯排序）。**本 PRD 的核心对象——报告库索引、Worldview、投资 Claim——在代码中尚不存在**。注意：现有代码里的 "claim"（`citationLedger`、`EvidenceAuditor` 等）指报告引用审计中的引文断言，与第 5 节的投资 Claim 是两回事，不可混淆。

## 9. 最小验收标准

**Opportunity 与股票核验**

- 一个 Opportunity 可以关联多只股票，每只股票都有独立的基础公司快照和适配判断。
- BasicCompanySnapshot 必须是一段不超过 1000 字的快速摘要，不得扩写成表格或公司深度报告。
- 没有基础资料、证券身份未确认或业务暴露不真实的股票不得进入 long candidate。

**Claim 与每日验证**

- Claim 必须有验证窗口、验证间隔、基线与目标、验证来源、因果段落、中间步骤和失效条件。
- 主要由不可预测随机事件主导且没有可观察中间信号的判断不能进入正式 Claim Store。
- Side System 每天扫描所有处于验证窗口的 Claims，并按 interval 形成深度 Observation。
- Reflection 同时判断最终结果与因果链，并分别回流 Worldview Reinforcement 和 Analyzer Reviewer。

**Worldview 与 Context**

- Worldview 保留不同观点及证据，但必须形成自己的 base view、置信度和改变条件。
- Worldview 的 canonical 文件是英文 `worldview.md`，尽量小于 100k tokens；超过前必须版本化压缩。
- 初读和复读 Context Manager 都应优先装载完整 current Worldview；不得静默截断或仅使用摘要。
- Worldview 内容由 LLM 柔性维护；确定性代码只控制 coverage、版本、lineage 和审计。

**排序与审计**

- ELO 必须展示 seed、分组/换组轮次、R、RD、`R-2×RD`、决赛和 degraded diagnostics。
- Claim、Observation 和旧 Worldview 版本不可被事后改写。
