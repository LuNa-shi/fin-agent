# Current Agent I/O Boundaries

> This document describes current runtime boundaries; generated workflow and Agent contract projections remain authoritative for hashes and field audits.

## Canonical Agent execution

All production Agent calls use `runDefinedAgent()` / `AgentExecutionRuntime` and the unified `IdempotentAgentBackend -> ConcurrentAgentBackend -> PiAgentBackend` composition. Existing investment-expert Prompt and ordered Tool Use assets are protected by Golden fixtures. Unless explicitly overridden, the repository default and the `small` / `main` / `reflection` tiers resolve to `openai-compatible/gpt-5.6-sol` with `high` reasoning. Provider or model unavailability fails closed; ordinary tests and CI use scripted/fake adapters and make no live/network attempts.

## Daily Report Batch and Report Overview admission

Scheduled report production creates one producer-owned `daily-report-batch.v1` per UTC production date. The immutable plan registers at most 100 intended items before any candidate staging or provider call; a larger plan fails closed. Before provider work, a durable compare-and-set checkpoint binds each item to one admission candidate and freezes its ReportVersion, content, fingerprint, analysis run, and Report Overview effective-config digests, so a different run or route cannot consume the same item. Candidate creation and checkpointing hold the same batch-item fence: the complete frozen candidate is created first and the checkpoint is written before that fence is released. A crash between those writes therefore leaves a recoverable candidate rather than a checkpoint with missing audit state. A genuinely unavailable checkpointed candidate is terminalized by recovery rather than recreated with reset attempt history, while an exact authoritative admission marker is replayed before current config or candidate-state handling and never calls the provider again. Each item receives one historical production/admission success or failure outcome. Recovery uses candidate and checkpoint truth to complete an open pending item if a process crashed before outcome recording. Closure is explicit, immutable, and idempotent, accepts any successful-report count, and publishes exactly one `worldview-processing-trigger.v1` result. Later candidate recovery is projected beside a closed historical item outcome and never reopens or mutates the closed batch.

Every producer and historical backfill uses `ReportAdmissionService`, the only standard post-producer seam. Before model execution it durably stages an exact `report-admission-candidate.v1`: normalized package bytes/digest/fingerprint, frozen lineage and source/batch association, effective Overview config digest, and its immediate-attempt budget. At that central seam, a daily producer package must resolve to an existing exact batch/item whose registered Project owns the package lineage; an ordinary producer cannot claim daily lineage, while backfill may preserve historical daily lineage but cannot claim a current batch item. The batch lock remains held while the candidate is atomically created and its item checkpoint is written, so a concurrent terminal outcome cannot split the two identities; a crash can leave a complete orphan candidate that recovery safely links, never a checkpoint-only reservation. A restarted worker consumes only the durable remainder of the initial immediate window; after real exhaustion, each later explicitly started worker grants one additional governed attempt. Exact marker replay is source-agnostic across producer and backfill, precedes current Agent-config resolution, repairs projections, and bypasses both provider work and exhausted backfill attempt budgets. Idempotent replay otherwise requires the same complete binding; any conflict or storage tamper fails closed. Candidate-scoped ownership uses a bounded lease, stable attempt identity/idempotency key, and per-candidate cross-process exclusion; the candidate lock is acquired before the short global staging fence, so a contended replay cannot block unrelated staging. Recovery handles lock contention per candidate and continues with independent work. A dead owner can be reclaimed without holding a filesystem lock across the model call, a live lock owner is never evicted by age alone, and contention is reported as retryable in-flight work rather than a terminal batch failure.

The private admission worker invokes tool-less `report-overview` on the configured `small` route with one bounded outer physical-call budget, including transient provider failures and schema-invalid output. Attempts, sanitized provenance, stop reasons, exponential backoff eligibility, and terminal/retryable state are durable. Budget exhaustion does not publish a ReportVersion. An explicitly started scheduled daily producer invokes worker recovery before new production work and may resume eligible candidates; ordinary server startup, CI, and read-only APIs never invoke recovery or the provider.

Once preparation succeeds, exact ReportVersion and private `report-overview.v1` bytes are placed as one hidden pair. An authoritative admission marker is committed last. Before that marker neither list nor detail exposes the report; after it, recovery rebuilds derived ingestion/index projections without another model call. A projection-repair exception after the marker remains retryable and cannot become a terminal batch failure; batch success is recorded only after those projections are repaired. Public Report Library surfaces expose only exact `Pending` or `Processed` processing state. Every nested batch DTO, historical ingestion read, and failure-event replay is normalized through closed allow-listed safe fields/codes/messages while preserving original evidence bytes; none exposes Overview readiness, an Overview route/card, raw provider text or payloads, credentials, endpoints, or local paths. Overview access exists only inside the frozen Canonical Worldview capability scope.

## Canonical Worldview and Claim Library publication v1

A new Daily Report Batch closure invokes `CanonicalWorldviewCoordinator.processTrigger()` through `DailyReportBatchAdmission`. The immutable trigger itself is not mutated; closure records `processingTarget=canonical-worldview-processing.v1`, and the producer composition resumes recoverable targeted triggers before new work. The globally serialized coordinator rebuilds Report Library projections, selects the oldest Reports whose exact receipt-derived status is `Pending`, caps selection at 100, applies the configured byte/token/time/tool bounds, and executes only the first bounded group. Configuration above the hard 100-Report maximum fails closed. Later admissions and Pending Reports outside that group remain Pending. One-group execution is the Issue #41 boundary; consecutive backlog draining and exhausted-run recovery belong to Issue #42.

Each group uses the five-node `canonical-worldview-processing.v1` WorkflowSpec with `workspaceMode=none`: freeze the run, execute bounded Core Agent attempts, validate Worldview plus Claim-action input, stage publication, and commit publication. Before the first attempt, `worldview-run-workspace.v1` atomically freezes the ordered ReportVersion manifest with admission sequence/content digest/fingerprint/capabilities, every digest-bound Overview and its content, the complete current Canonical Worldview package or explicit bootstrap null, complete current Claim records, a compact `claimId/version/assertion` table, effective provider/model/reasoning and Prompt/config identity, whole-Agent and model-API retry policies, token/time/tool bounds, approved capabilities, stable run/workspace identities, and `workspaceDigest`. The stored file is immutable and digest-verified. A retry does not reselect Reports, reload current Worldview/Claims, or adopt changed configuration.

One logical Core Worldview Agent run permits at most three complete Agent attempts. Each complete attempt starts a fresh conversation over the same frozen workspace. Inside each attempt, the model API/transport layer independently permits at most five attempts for retryable failures. The layers intentionally coexist and can produce at most 15 model API attempts. Both whole-Agent attempts and `modelApiAttempts` are persisted in Processing Log audit with the same workspace identity/digest. Retryable Agent/runtime or mechanical Worldview-result failures can start the next complete attempt. An invalid individual Claim item does not. Workspace corruption, digest failure, permission denial, or permanently invalid route/config fails closed. Exhaustion records `FAILED_EXHAUSTED`; it preserves workspace and safe attempt audit, publishes no Worldview/Claims/receipts, and leaves every Report Pending.

`worldview_read_current`, `worldview_enumerate_overviews`, `worldview_read_report_version`, and `worldview_search_claims` are internal no-cache, read-only, attempt-scoped capabilities. They read only the frozen current Worldview, complete frozen Overview set, exact in-range ReportVersions, and frozen Claim assertion table. Runtime authorization denies a different scope, out-of-range ReportVersion, arbitrary filesystem paths/tools, external retrieval, or any write. Exact full reads are digest-verified and recorded in a safe ID/digest/fingerprint ledger; raw report bodies are redacted from generic trace projections.

The strict result contract is `worldview-agent-result.v1` with separate ordered `worldview` and `claimActions` sections. The Agent decides `KEEP` or `UPDATE` first, then compares materially touched judgments against every frozen Claim assertion and emits zero or more `ADD`, `UPDATE`, or `NOOP` items. Canonical Worldview and Claim Library are semantically separate. A Claim stores no Worldview Version or KEEP Evaluation foreign key; they share only `runId` / `publicationId` audit. They still publish atomically in one run, so an invalid Worldview prevents all Claim and receipt publication.

Worldview validation is deterministic contract, evidence, full-read lineage, coverage, identity, digest, and package-integrity validation. Bootstrap cannot `KEEP`; `KEEP` has no replacement package and writes one `worldview-evaluation-record.v1`; `UPDATE` publishes one complete seven-document `canonical-worldview-package.v1`, one append-only `worldview-update-record.v1`, and a rebuildable `current-worldview.v1`. Overview text is discovery-only and cannot be direct evidence.

The Core Agent is the sole semantic authority for Claim similarity and action choice. Deterministic code does not fuzzy-match, semantic-deduplicate, or rewrite one action into another. Claim Library v1 validates each raw Claim action independently after Worldview validation. `ADD` carries a complete immutable v1 body and derives `claimId` from run/action identity. `UPDATE` targets an exact frozen `{claimId, expectedVersion}` and carries the complete next body. `NOOP` targets the exact frozen version and writes audit without a new Claim version. Each Claim body includes one-line `assertion`, subject, optional tickers, causal rationale, verification point/window, metric, acceptance and invalidation conditions, and exact ReportVersion evidence.

Malformed, stale-target, conflicting, unsupported, or evidence-ineligible Claim items are stored as durable rejections with stable safe reasons; unrelated valid items continue, and an invalid `UPDATE` leaves the current Claim unchanged. Duplicate `actionId` and same-target conflicts use the owner-approved first-valid-wins rule: only a successfully accepted item reserves that identity/target, and every later conflict is rejected. `ADD`/`UPDATE` evidence requires at least one newly digest-verified full ReportVersion read from this workspace; `UPDATE` may retain prior evidence, and `NOOP` records at least one newly read exact reference. Storage, integrity, locking, or publication failure is not partially rejectable and aborts the whole publication.

A successful run stages the Worldview outcome, Claim versions/actions/rejections, safe attempt audit, and one exact `processed-report-version-receipt.v1` per frozen ReportVersion. It then commits one authoritative `worldview-run-publication-marker.v1`, whose digest binds every staged object. In active composition the Claim Store reads completion from this run marker; its standalone local marker is disabled. Before the marker, active Worldview, Claim Library, and Report Library projections expose none of the staged changes. After the marker, rebuild/replay exposes the same publication without another Agent call or duplicate history. Report processing state comes only from an exact receipt match on ReportVersion ID, admission sequence, content digest, and fingerprint; exact completed receipts are the sole processing-status authority.

Read-only Canonical Worldview APIs are `/api/worldview/current`, `/api/worldview/processing-log`, run detail, `/api/worldview/evaluations`, `/api/worldview/versions`, and version detail. Read-only Claim Library APIs are `/api/claims`, Claim detail (optionally by version), `/:claimId/history`, `/:claimId/actions`, `/api/claims/actions`, and `/api/claims/rejections`. Processing Log detail includes Worldview outcome, accepted/rejected Claim actions, rejection reasons, complete Agent/model-API attempt audit, and exact Processed receipts. The frontend exposes a compact Claim Library list, Claim detail/version/action history, Claim outcomes in Worldview run detail, and separate Worldview Versions. There is no Claim mutation, administration, verification-scheduler, or ticker-dashboard product.
